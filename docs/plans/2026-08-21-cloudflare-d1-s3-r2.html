Overview

DBcooper today speaks Postgres, SQLite, Redis, and ClickHouse, plus ForgeGraph account discovery. This plan adds two remote SQLite surfaces and an object browser. Cloudflare is an account-level integration: a settings token discovers D1 databases and R2 buckets. Turso is a regular connection type (database URL + auth token). Both D1 and Turso reuse the SQLite UI over HTTP. Object storage is a new file-manager surface that also ships as a generic S3 connection type for AWS, MinIO, Garage, and hand-keyed R2.

Goals & Non-goals

Goals

  • Save a Cloudflare API token (and account ID) in Settings, test it, and sync resources.
  • Sidebar section listing D1 databases and R2 buckets, ForgeGraph-style.
  • D1 uses the existing SQLite UI: tables, grid, query editor, row insert/edit, schema viz.
  • Turso as an Add-connection type (libSQL/HTTPS URL + database auth token) with that same SQLite UI.
  • Generic S3 connection type plus an object browser: browse, preview, upload, download, delete, copy/rename.
  • R2 discovered from the token opens in that same browser.

Non-goals

  • Standalone “Add D1 connection” type (token is account-level).
  • Turso Platform API org discovery, creating databases, embedded replicas, or Turso Sync.
  • Create/delete D1 databases, wrangler import, or D1 time travel.
  • Create/delete S3 buckets, versioning, lifecycle, CORS, or presigned-upload widgets.
  • Multiple Cloudflare accounts at once.
  • Workers bindings, Hyperdrive, or KV/Queues.

Decisions

  • Hybrid product model. Cloudflare is an account, not a connection type. S3 and Turso are local connection types. D1 is discovery-only in v1.
  • Cloudflare token never lands on connection rows. Same as ForgeGraph: settings hold the secret; cache stores metadata only. Turso’s database token does live on the connection row — that is how Turso auth works.
  • R2 S3 credentials. Happy path derives Access Key ID from GET /user/tokens/verify (token id) and Secret from SHA-256 of the token value. Optional explicit R2 keys in Settings if derivation fails (scoped Object Read tokens, account tokens, etc.).
  • D1 and Turso are DatabaseDrivers. Both reuse SQLite catalog SQL and the SQLite UI. D1 talks Cloudflare REST; Turso talks Hrana over HTTP (/v2/pipeline) with reqwest — no native libsql crate in v1.
  • S3 is not a DatabaseDriver. Separate Tauri commands. ConnectionDetails is already too large — new component tree under src/components/s3/.
  • New extra JSON column on connections for S3 region, endpoint, path-style, prefix. Access key / secret stay in username / password; bucket in database. Turso stores the URL on host and the auth token on password.

D1 query contract and SQL reuse

Endpoint: POST https://api.cloudflare.com/client/v4/accounts/{account_id}/d1/database/{database_id}/query

Body: {"sql": "...", "params": [...]}. Response result[0].results is an array of objects; meta.changes / meta.duration map onto QueryResult.

Reuse existing SQLite catalog SQL in database/queries/sqlite.rs (sqlite_master, pragma_table_info, foreign keys, indexes). D1 is SQLite-compatible enough for these.

Table pagination stays in SQL (LIMIT/OFFSET) so we do not pull whole tables over HTTP. Query editor runs raw SQL as today.

Row insert/update/delete already generate SQL in the frontend; the driver just executes it. No D1-specific grid.

Turso HTTP contract and field mapping

Accept libsql://… and https://…. Normalize to https://{host}/v2/pipeline. Auth header: Authorization: Bearer {token}.

POST /v2/pipeline
{
  "requests": [
    { "type": "execute", "stmt": { "sql": "SELECT 1" } },
    { "type": "close" }
  ]
}

Map results[0].response.result.cols / rows / affected_row_count onto QueryResult. Hrana rows are typed (integer, float, text, blob, null); integers arrive as strings to preserve i64.

Reuse the same SQLite catalog SQL as D1. Catalog + pagination + row SQL live in the existing frontend; the driver only executes.

pub struct TursoConfig {
    pub url: String,       // https host, no /v2/pipeline suffix stored
    pub auth_token: String,
}

// connection row

// host     = normalized https URL
// password = auth token

v1 does not wrap the native libsql crate (binary size, extra native deps). If Hrana HTTP is missing a needed feature, revisit — not the default.

Risks & Mitigations

RiskSeverityMitigation
A dashboard API token may not derive valid R2 S3 keys (id + SHA-256 is documented for tokens created via the Tokens API / R2 token UI). High Optional explicit R2 access key + secret in Settings. On object-list failure, show that fallback, not a generic 403.
One token often lacks both D1 and R2 permission groups. Medium Sync is best-effort per kind: D1 list failing does not hide R2, and vice versa. Surface partial errors on the tree.
D1 REST is rate-limited and caps response size (~10MB) and query duration. Medium Keep table pagination; pass through API errors; no “load entire table”.
Full aws-sdk-s3 bloats the Tauri binary. Medium Start with the smallest crate that supports ListObjectsV2 + multipart; measure bun run tauri build size before merging.
ConnectionDetails.tsx is already huge; stuffing S3 into it will make it worse. High Hard rule: S3 UI lives in src/components/s3/. Details page only branches and mounts.
D1 / Turso PRAGMA / sqlite_master quirks vs local SQLite. Low If a catalog query fails, fall back to simpler PRAGMA table_info per table. Schema viz degrades rather than blanking. Shared fallback for both remote SQLite drivers.
Hrana HTTP row types (i64 as strings, blobs as base64) mismatch the SQLite json mapping. Medium Centralize Hrana value decoding in turso.rs. Tests cover integer/float/text/blob/null. Do not pull in the native libsql crate unless HTTP is insufficient.
Users paste a Turso platform API token instead of a database token. Low Test-connection error copy: “Use a database auth token from turso db tokens create, not the platform API token.”

Open Questions

Settled in this draft: hybrid Cloudflare discovery + generic S3; D1 is read/write SQLite UI and discovery-only; Turso is an Add-connection type (URL + database token) over Hrana HTTP; S3 v1 is a full file manager.
Deferred: jurisdiction-specific R2 endpoints (.eu.r2.cloudflarestorage.com etc.). Turso Platform API org listing / embedded replicas. v1 can store R2 jurisdiction in extra if the list-buckets payload includes it, but custom endpoints per bucket wait until someone hits a jurisdictional bucket.
